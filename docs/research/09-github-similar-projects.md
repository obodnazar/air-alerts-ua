Дата дослідження: 11.10.2026, ~23:30 Київ. Метод: `gh search repos/code` (англійські й українські запити) + читання README, дерев'я файлів, issues і комітів через `gh api`. Усі "оновлено" нижче беруться з `pushed_at` / дат комітів, які повернув GitHub.

## 2. Ідеї, які беремо (за співвідношенням цінність/зусилля для ~12 год збірки)

### Tier A: робимо обов'язково (мало зусиль, велика цінність)

1. **Пакет чистки даних і coverage-cutoff** (Nazar32, AnnaKiulafli, tannyaQ, IvanSnezhok, yevayarova). ~1 год.
   - Точна дедуплікація; UTC -> `Europe/Kyiv` по кожній мітці (DST: 08:00 Києва = 05:00 UTC влітку, 06:00 UTC взимку); фільтр `level == "raion"`; злиття перетинних інтервалів у межах raion+дата; виключити нульові/від'ємні/аномально довгі (IvanSnezhok обмежує 12 год, AnnaKiulafli 7 діб); повний календар із нулями; виключити Луганську/Крим.
   - **Головне:** задати `data_coverage_end` для кожного джерела (official = 07.09.2026) і не рахувати відсутні рядки після нього як "немає тривоги". IvanSnezhok прямо описує цей баг для live-режиму.

2. **Сходинки базових ліній + BSS.** ~1 год. (IvanSnezhok, Nazar32, alitskevych)
   - Кліматологія "та сама година, 28 д" (по raion), persistence (тривога о 07:00 -> о 08:00), Markov (стан у 20:00/07:00), **rolling-Markov 42 д**. У Nazar32 саме rolling-Markov переміг paired CI проти ML на контрольному 2024 (9.35 % vs 6.21 %), тож це обов'язкова лінія. Метрики: Brier, BSS проти кліматології, reliability, log loss; MASE не потрібен для ймовірнісної цілі.
   - **[висновок]** для 08:00 з прогнозу о 20:00 очікуємо малий приріст над кліматологією: IvanSnezhok бачить +2-5 % за межами 1 години. Це треба сказати чесно в звіті, а цінність показати в cost-шарі.

3. **Leakage-тести як механічна перевірка** (IvanSnezhok). ~1.5 год. Це пряма відповідь на "zero leakage".
   - Тест усікання: для випадкових T перебудувати ознаки з даних, усічених у T, і порівняти з повним пайплайном.
   - Тест міток: стерти історію до T не повинно міняти мітку.
   - Тест "мітка не в ознаках" + guard `AUC > 0.995 -> abort`.
   - Навмисна ін'єкція витоку (lag-0 ознака; "хвилин від кінця останньої тривоги", що використовує кінець тривоги, яка ще триває), щоб довести, що тест кусається.
   - Embargo між train і evaluation: мітка о 08:00 вчора не перетинається з ознаками сьогодні.

4. **Survival-модуль у формі koalla05 з коректною цензурою.** ~2 год.
   - KM + умовна `S(t+Δ)/S(t)`; емпіричний умовний квантиль; опційно LightGBM binary "відбій до контрольної точки". Конкретно: умова "тривога активна о 08:00, минуло t хв", ціль "відбій до 09:00/10:00/11:00".
   - `naive=True` обробляємо як **праве цензурування в 30 хв** (а не як справжню тривалість; tannyaQ тільки виключає їх, ми можемо зробити краще, і це вимагає перевірки, що не зсуває KM). `end: null` у alerts.in.ua теж цензура.
   - Порівняти KM по режимах: до/після зонування, по годинах доби (ранкові тривоги тривають інакше).

5. **Пререгістрація + парні CI** (Nazar32). ~45 хв. Короткий `PREREG.md`, створений **до** запуску на тестовому вікні: вікна train/val/test, кандидати, правило відбору (проста модель, якщо в межах 1 SE), критерій успіху. Парні block-bootstrap CI (блоки по 3 дні) різниць Brier між моделлю і лінією. Згадати чесно, що вікно 2026 уже бачили розвідувально (Nazar32 зробив саме так: Disclosure-рядок).

### Tier B: сильно підсилює (середні зусилля)

6. **Контрфактуал "oblast_any" для зонування** (Nazar32). ~1.5 год. Той самий день і та сама ознака: мітка_raion vs мітка_oblast_any (будь-який raion області під тривогою о 08:00). Різниця = частка шкільних ранків, які зонування врятувало. Перехресна перевірка: volunteer-файл (oblast-level, оновлюється щодня) як незалежна оцінка oblast-wide до та після 15.12.2025. Це відповідає add-on (a) без жодних нових даних.

7. **Cost-шар через політики рішень** (Nazar32: static / reactive / oracle / forecast + поріг перемикання `eps`). ~2 год.
   - Політики: (i) реактивна за листом МОН (дивимось о 08:00), (ii) на основі прогнозу в 20:00 ("попередь батьків: ймовірно дистанційка"), (iii) oracle. Втрата: student-hours (учні × хвилини дистанційки; параметр "розмір школи" як сценарій) + штраф за хибний "очно" (дитина в дорозі під час тривоги) з явним співвідношенням витрат, що ми підбираємо як сценарій, а не оцінку.
   - Вибір контрольної точки 09/10/11 з мінімуму очікуваних втрат по raion, на основі survival з п. 4.
   - Поріг рішення вибирається на валідації (Nazar32: `eps` фіксують до перегляду test).

8. **Рекалібровка по raion** (Nazar32: щоденно, останні 42 доби дозрілих цілей, зсув logit (Newton), shrinkage `d/(d+14)`, `|offset| <= 1.5`) або ізотонічна на окремому місяці. ~1 год. Корисно, бо raion-режим новий, а base rate дрейфує.

9. **Розділити "вже триває" і "нова тривога"** (IvanSnezhok: його перша ціль була надто легкою, бо більшість -- persistence). Для прогнозу 07:00 -> 08:00 звітувати skill окремо для двох підмножин; для 20:00 увесь сигнал у "новій тривозі". ~30 хв.

10. **Метрики всередині регіону, не pooled** (IvanSnezhok: pooled AUC лестить, within-region onset-3h AUC лише 0.52-0.74, skill від -4 % до +10 %). Таблиця skill по raion + мінімальний поріг `n` (colobocman). ~30 хв.

### Tier C: приємні додатки, якщо лишиться час

11. **Візуалізація "смуга дня"** (Ant0013/tryvohy): для кожного шкільного дня інтервал 08:00-контрольна точка та перекриття тривогою, окремий шар city/obl, прапорець "тривала через межу вікна". Плюс теплокарта година x день тижня (Semfayni, lyriKgt) і reliability-діаграма.
